PART 2: Paano Masasabing Secured ang System & Code Level?

1. Proteksyon Laban sa SQL Injection (SQLi)

100% ng dynamic database transactions ay gumagamit ng PDO Parameterized Prepared Statements. Walang direct string concatenation ng user inputs sa SQL queries. Ligtas itong tinatrato ng database bilang literal values at hindi executable commands.

2. Proteksyon Laban sa Cross-Site Scripting (XSS)

Ang lahat ng ipinapasok na datos mula sa form inputs at URL parameters ay sinasala gamit ang output encoding (htmlspecialchars($data, ENT_QUOTES, 'UTF-8')) bago i-render sa browser. Ang mga script tulad ng <script>alert(1)</script> ay nagiging plain text lamang.

3. Proteksyon Laban sa Brute Force Attacks (Login Rate Limiting & Temporary Lockout)

Gumagamit ang system ng Temporary Rate Limiting (5 failed attempts within 15 minutes) alinsunod sa OWASP authentication guidelines. Kapag umabot sa 5 sunod-sunod na maling password, awtomatikong pinapatawan ang account ng 15-minute temporary restriction na may countdown sa screen.

  • Bakit Temporary Restriction imbes na Permanent Lockout? Upang maiwasan ang Account Lockout Denial-of-Service (DoS) Attack kung saan sadyang ini-enter ng attacker ang username ng guro o admin para i-lock sila palabas. Pinapayagan din nito ang mga lehitimong gumagamit na makabalik nang kusa pagkatapos ng 15 minuto nang hindi naiistorbo ang Administrator.
  • Immediate Admin Override: May nakalaang One-Click Unlock button ang Administrator sa users.php para ma-clear agad ang restriction sakaling personal na humingi ng tulong ang estudyante o guro sa tanggapan.

4. Proteksyon sa File Uploads (Anti-Malware & Web Shell)

  • Strict Extension Whitelist: Tanging .pdf, .jpg, .jpeg, at .png lamang ang pinapayagan. Bawal ang anumang .php o .exe.
  • File Size Cap: Hanggang 10MB lamang bawat file.
  • Filename Sanitization: Pinalitan ang file name gamit ang unique timestamps at hashes upang maiwasan ang directory traversal at file overwriting.

PART 3: Paano Masasabing Secured ang Website & Server Infrastructure?

1. 256-Bit TLS/SSL Encryption (HTTPS)

Lahat ng komunikasyon sa pagitan ng browser at server ay encrypted. Makikita ang Padlock Icon 🔒 sa browser. May automated rule sa .htaccess na pumupwersa sa lahat ng http:// patungo sa secure na https://.

2. Anti-Directory Browsing (Options -Indexes)

Nakatago ang mga directory ng website. Kapag binuksan ng publiko ang https://iadminconnect.com/uploads/ o /config/, lalabas ang 403 Forbidden.

3. Uploads Execution Shield (uploads/.htaccess)

Kahit makapaglusot ng script ang isang attacker sa upload folder, hindi ito ie-execute ng server dahil may FilesMatch security rule na humaharang sa lahat ng server-side executable scripts.

4. HTTP Security Response Headers (OWASP Standards)

  • X-Frame-Options: SAMEORIGIN – Hinaharang ang Clickjacking (bawal i-iframe ang portal sa ibang phishing site).
  • X-Content-Type-Options: nosniff – Pinipigilan ang MIME-type sniffing ng mga browser.
  • X-XSS-Protection: 1; mode=block – Built-in anti-XSS protection sa mga modernong browsers.

PART 4: Paano Pinoprotektahan ang Data ng Paaralan at Estudyante?

(Data Privacy Act of 2012 / RA 10173 Compliance)

1. Principle of Least Privilege & Strict Data Isolation

Ang bawat estudyante o guro ay may access lamang sa sarili nilang mga dokumento (WHERE user_id = :session_id). Hindi nila masisilip ang requests o attachment ng ibang tao.

2. Immutable Audit Trail & System Logs (Accountability)

Alinsunod sa RA 10173, ang bawat kritikal na galaw sa system ay awtomatikong itinatala sa audit_logs table:

  • User Name at Role: Sino ang gumawa?
  • Action Performed: Ano ang ginawa? (hal. Marked Request RQ-045 as Completed)
  • IP Address: Saan nanggaling ang request?
  • Exact Timestamp: Kailan nangyari?

PART 6: Technical Code Reviewer & Architecture Deep-Dive (Start to Finish)

Gamitin ang bahaging ito kapag tinanong ng panel ang mismong code structure, logic, algorithms, at data flow ng i-AdminConnect.

1. Request Processing Lifecycle (submit_request.php → request_details.php)

Core Code Logic

A. Dynamic Payload Aggregation & Role Filtering:

Bago mag-load ang form, kinukuha lamang ng system ang mga dokumentong otorisado sa role ng user (WHERE target_role = :role OR target_role = 'both'). Kapag pinili ang dokumento, may nakalaang dynamic fields:

  • Teacher COE: Kinukuha ang Employee Number, Salary Grade, Step, Date Hired, at With Compensation (Yes/No).
  • Teacher Certificate of Rating (CR): Kinukuha ang numerical IPCRF points sa tatlong magkakasunod na school years at kinukwenta ang average rating.
  • Student GMC / COG / COE: Kinukuha ang Section/Strand, Student Status (Currently Enrolled vs Graduated), Graduation Year, at Target School/Purpose.
  • Student Form 137 / SF10: Mandatory ang pag-upload ng official request letter o Valid ID bago tanggapin.

Lahat ng mga specific inputs na ito ay ini-serialize at ini-imbak sa additional_notes column nang maayos at may label upang madaling basahin ng Administrator at Registrar.

B. Collision-Proof Tracking Number Algorithm:

Hindi kami gumagamit ng simple COUNT(*) dahil kapag may naburang record o may seeded historical data, magkakaroon ng primary/unique key collision. Sa halip, kinukuha namin ang pinakamataas na numeric value gamit ang Regex extraction:

// Dynamic Extraction ng Maximum Numeric Tracking Number
$stmt = $pdo->query("SELECT MAX(CAST(SUBSTRING(tracking_number, 4) AS UNSIGNED)) as max_num 
                     FROM requests WHERE tracking_number REGEXP '^RQ-[0-9]+$'");
$max_num = (int)($stmt->fetchColumn() ?? 0) + 1;
$tracking_num = 'RQ-' . str_pad($max_num, 3, '0', STR_PAD_LEFT); // hal. RQ-001, RQ-045, RQ-102

C. Smart Guard File Upload Sanitization:

Ang bawat attachment ay dumadaan sa tatlong pagsusuri:

  1. Extension Whitelist: in_array($ext, ['pdf', 'jpg', 'jpeg', 'png'])
  2. Size Cap: $file_size <= 10 * 1024 * 1024 (Maximum 10MB bawat file).
  3. Collision & Traversal Shield: Ang filename ay pinalitan gamit ang timestamp at regex cleaning: 
    $unique_name = time() . '_' . $i . '_' . preg_replace('/[^a-zA-Z0-9._-]/', '_', $file_orig_name);

Ang metadata ng lahat ng na-upload na files ay ini-encode bilang JSON array sa attached_filename: [{"name":"Valid_ID.pdf", "file":"1795...pdf", "size":"1.2 MB"}].

D. 4-Stage Status Pipeline:

Ang request ay sumasailalim sa automated 4-stage pipeline:

  • Stage 1 (Submitted): Naitala sa database ang timestamp (stage1_time).
  • Stage 2 (Processing): Awtomatikong pumapasok sa Stage 2 kapag nai-submit upang agad masimulan ng tanggapan.
  • Stage 3 (Ready for Release): Kapag na-verify at napirmahan na ng Registrar/Admin. May kasamang Scheduled Claim Date.
  • Stage 4 (Completed): Kapag nakuha na ng humihiling ang pisikal na dokumento at nag-acknowledge ng resibo.

2. Email Notification System (Native SMTP Socket Client – includes/mailer.php)

Network & Email Engine

A. Bakit Native Stream Socket sa Halip na PHPMailer / External Libraries?

Hindi kami nag-install ng mabibigat na external Composer dependencies (tulad ng vendor/phpmailer). Ang aming mailer ay Purong Native PHP gamit ang stream_socket_client(). Ito ay:

  • Zero Dependencies: Hindi masisira kahit magbago ang PHP version ng Hostinger o XAMPP.
  • Ultra-Lightweight & Fast: Tumatakbo sa loob lamang ng 200–400 milliseconds.
  • Direct RFC 5321 / 5322 Protocol Control: Diretso itong nakikipag-usap sa Google SMTP server sa pamamagitan ng standard mail commands.

B. Paano Nakikipag-usap ang Code sa Gmail SMTP Server:

// 1. Pagbukas ng Socket sa Port 587
$socket = stream_socket_client("tcp://smtp.gmail.com:587", $errno, $errstr, 10);

// 2. Handshake at Pag-upgrade sa TLS Encryption
fputs($socket, "EHLO " . gethostname() . "\r\n");
fputs($socket, "STARTTLS\r\n");
stream_socket_enable_crypto($socket, true, STREAM_CRYPTO_METHOD_TLS_CLIENT);

// 3. Authentication gamit ang Base64 Google App Password
fputs($socket, "AUTH LOGIN\r\n");
fputs($socket, base64_encode($smtp_user) . "\r\n");
fputs($socket, base64_encode($smtp_pass) . "\r\n");

// 4. Mail Headers at HTML Content Injection
fputs($socket, "MAIL FROM: <$from_email>\r\n");
fputs($socket, "RCPT TO: <$to_email>\r\n");
fputs($socket, "DATA\r\n");
// Inilalagay ang Subject, MIME-Version, Content-Type: text/html, at HTML Body
fputs($socket, ".\r\n"); // Tapos na ang email message
fputs($socket, "QUIT\r\n");

C. Kailan Nagpapadala ng Email ang System?

  1. Registration OTP: Nagpapadala ng 6-digit verification code sa email ng bagong rehistrong estudyante o guro.
  2. New Request Submission: Kinukumpirma ang submission at ibinibigay ang RQ-XXXXXX tracking number.
  3. Status Updates: Kapag naging Ready for Release (nakalagay ang eksaktong petsa at oras ng pagkuha) o kapag na-reject (nakalagay ang dahilan upang maayos ng estudyante).

D. Fault-Tolerant Fallback Mechanism:

Kung sakaling mawalan ng internet o magkaroon ng network timeout ang SMTP, hindi magka-crash o mag-e-error 500 ang system. May nakabalot na try-catch block na magre-return ng graceful status, magtatala sa audit_logs, at papasok pa rin ang abiso sa in-app notification bell. Tuloy-tuloy ang transaksyon ng user nang walang aberya.

3. Real-Time Synchronization & Live Cloud Architecture

Cloud & Sync Architecture

A. Live GitHub Deployment Engine (update.php):

Upang maiwasan ang mabagal at prone sa error na manual FTP file upload, gumawa kami ng automated deployment endpoint:

  • Kumukuha ito ng pinakabagong production code nang direkta mula sa GitHub repository raw.githubusercontent.com.
  • Gumagamit ng Cache-Busting Stream (?v=time()) upang matiyak na hindi lumang CDN cache ang makuha.
  • Awtomatikong lumilikha ng mga kinakailangang subfolder (@mkdir($dest_dir, 0755, true)) at sumusulat gamit ang atomic file_put_contents().

B. Automated Database Schema Healing & Migration:

Kapag nag-deploy ng bagong feature (halimbawa, ang lockout_time column para sa rate limiting), kusa itong ini-inject ng system sa MySQL table gamit ang INFORMATION_SCHEMA verification. Hindi kailangang mag-manual import ng SQL sa phpMyAdmin tuwing may update.

C. Asynchronous Session Keepalive (keepalive_api.php):

Upang hindi ma-kick out ang gumagamit habang nagta-type ng mahabang dahilan sa form, may event listener sa JavaScript (mousedown, keydown, scroll) na nagpapadala ng lightweight ping sa keepalive_api.php bawat 1 minuto. Ina-update nito ang $_SESSION['last_activity'] = time() sa server sa background nang walang page refresh.

D. Non-Blocking Public Tracking Modal (track_api.php):

Sa landing page (index.php), maaaring mag-track ang kahit sino gamit ang tracking number kahit hindi naka-login. Tumatakbo ito via asynchronous fetch('track_api.php?tracking_number=...') na nagbabalik ng JSON response at nag-a-update ng step-tracker progress bar sa loob ng modal nang walang reload.

4. Database Architecture & Query Security (PDO Standards)

Database Security

A. 100% Prepared Statements (Zero SQL Injection):

Lahat ng SQL queries sa buong system ay gumagamit ng PHP Data Objects (PDO) na may parameterized placeholders:

// Ehemplo ng Ligtas na Query sa i-AdminConnect
$stmt = $pdo->prepare("SELECT * FROM requests WHERE tracking_number = ? AND user_id = ?");
$stmt->execute([$tracking_number, $user_id]);
$request = $stmt->fetch();

Ang anumang SQL injection payload (tulad ng ' OR 1=1 --) ay itinuturing ng MySQL engine bilang isang literal na string value lamang, kaya imposibleng ma-manipula ang query structure.

B. One-Way Cryptographic Password Hashing:

Hindi kailanman iniimbak ang mga password sa plain text. Gumagamit kami ng BCrypt algorithm na may awtomatikong cryptographic salt:

  • Paglikha ng Account: $hash = password_hash($password, PASSWORD_DEFAULT); (Gumagawa ng 60-character high-entropy hash).
  • Pag-login: if (password_verify($input_password, $stored_hash)) { ... } (Pinipigilan ang timing attacks gamit ang constant-time string comparison).
