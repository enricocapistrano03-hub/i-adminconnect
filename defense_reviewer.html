Project Title: i-AdminConnect: An Automated Administrative Services & Record Tracking System
Live Production Portal: https://iadminconnect.com • Target Architecture: Web-Based Cloud Application

PART 1: Paano Ginawa ang System from Start to Finish?

(Metodolohiya: Software Development Life Cycle - Iterative & Agile Methodology)

Phase 1: Requirements Gathering & Problem Analysis

  • Ang Suliranin: Mano-manong logbook, matagal na pagpila sa Registrar, kakulangan sa live tracking ng dokumento, at nawawalang physical paper trails.
  • Ang Solusyon: Binuo ang isang centralized online platform para sa apat na authorized roles: Student, Teacher, Registrar, at System Administrator.
  • Ang 4-Stage Lifecycle Model: 1. Submitted → 2. Processing → 3. Ready for Release → 4. Completed & Claimed.

Phase 2: System Architecture & Database Modeling

  • Database (MySQL / MariaDB):
    • users – LRN, email, encrypted passwords, roles, at failed login counter.
    • requests – Unique tracking IDs (hal. RQ-045), multi-copy requests, layunin, at stage timestamps.
    • request_types – Mga opisyal na dokumentong pwedeng i-request (TOR/Form 137, Good Moral, Rating, atbp.).
    • notifications – Real-time in-app alerts para sa staff at estudyante.
    • audit_logs – Immutable activity ledger na may IP addresses alinsunod sa Data Privacy Act (RA 10173).
  • UI/UX Design: Responsive layout gamit ang institutional green branding, custom Plus Jakarta Sans typography, at sticky navigation.

Phase 3: Implementation & Coding (Tech Stack)

  • Frontend: Modern HTML5, Responsive CSS3 (Flexbox/Grid), Vanilla JavaScript (ES6+ Fetch API para sa asynchronous real-time tracking nang walang page refresh).
  • Backend: Native PHP 8.x – magaan, napakabilis, walang mabigat na framework overhead, at optimized para sa institutional cloud hosting.
  • Database Access: 100% PDO (PHP Data Objects) na may parameterized prepared statements.
  • Notification Services: PHPMailer / SMTP para sa automated claiming advisories at 6-digit OTP codes.
  • Bulk Processing Engine: Batch upload parser na may database transactions (500+ records nai-insert sa loob ng 1 segundo).

Phase 4: Testing & Quality Assurance

  • Functional Testing: Sinubukan ang bawat end-to-end workflow mula submission, evaluation, approval, claiming, hanggang completion.
  • Security Testing: Sinubukang pasukin gamit ang SQL Injection, Cross-Site Scripting (XSS), Brute Force, at URL tampering.
  • Load/Batch Testing: In-optimize ang bulk import gamit ang auto-correct sa human typos sa emails.

Phase 5: Cloud Deployment & Maintenance

  • Live Hosting: Hostinger Cloud LiteSpeed Web Server gamit ang live domain na https://iadminconnect.com.
  • Security Layer: 256-bit TLS/SSL certificate, .htaccess server hardening, at automated GitHub live-sync pipeline (update.php).

PART 2: Paano Masasabing Secured ang System & Code Level?

1. Proteksyon Laban sa SQL Injection (SQLi)

100% ng dynamic database transactions ay gumagamit ng PDO Parameterized Prepared Statements. Walang direct string concatenation ng user inputs sa SQL queries. Ligtas itong tinatrato ng database bilang literal values at hindi executable commands.

2. Proteksyon Laban sa Cross-Site Scripting (XSS)

Ang lahat ng ipinapasok na datos mula sa form inputs at URL parameters ay sinasala gamit ang output encoding (htmlspecialchars($data, ENT_QUOTES, 'UTF-8')) bago i-render sa browser. Ang mga script tulad ng <script>alert(1)</script> ay nagiging plain text lamang.

3. Proteksyon Laban sa Brute Force Attacks (Login Rate Limiting & Temporary Lockout)

Gumagamit ang system ng Temporary Rate Limiting (5 failed attempts within 15 minutes) alinsunod sa OWASP authentication guidelines. Kapag umabot sa 5 sunod-sunod na maling password, awtomatikong pinapatawan ang account ng 15-minute temporary restriction na may countdown sa screen.

  • Bakit Temporary Restriction imbes na Permanent Lockout? Upang maiwasan ang Account Lockout Denial-of-Service (DoS) Attack kung saan sadyang ini-enter ng attacker ang username ng guro o admin para i-lock sila palabas. Pinapayagan din nito ang mga lehitimong gumagamit na makabalik nang kusa pagkatapos ng 15 minuto nang hindi naiistorbo ang Administrator.
  • Immediate Admin Override: May nakalaang One-Click Unlock button ang Administrator sa users.php para ma-clear agad ang restriction sakaling personal na humingi ng tulong ang estudyante o guro sa tanggapan.

4. Proteksyon sa File Uploads (Anti-Malware & Web Shell)

  • Strict Extension Whitelist: Tanging .pdf, .jpg, .jpeg, at .png lamang ang pinapayagan. Bawal ang anumang .php o .exe.
  • File Size Cap: Hanggang 10MB lamang bawat file.
  • Filename Sanitization: Pinalitan ang file name gamit ang unique timestamps at hashes upang maiwasan ang directory traversal at file overwriting.

PART 3: Paano Masasabing Secured ang Website & Server Infrastructure?

1. 256-Bit TLS/SSL Encryption (HTTPS)

Lahat ng komunikasyon sa pagitan ng browser at server ay encrypted. Makikita ang Padlock Icon 🔒 sa browser. May automated rule sa .htaccess na pumupwersa sa lahat ng http:// patungo sa secure na https://.

2. Anti-Directory Browsing (Options -Indexes)

Nakatago ang mga directory ng website. Kapag binuksan ng publiko ang https://iadminconnect.com/uploads/ o /config/, lalabas ang 403 Forbidden.

3. Uploads Execution Shield (uploads/.htaccess)

Kahit makapaglusot ng script ang isang attacker sa upload folder, hindi ito ie-execute ng server dahil may FilesMatch security rule na humaharang sa lahat ng server-side executable scripts.

4. HTTP Security Response Headers (OWASP Standards)

  • X-Frame-Options: SAMEORIGIN – Hinaharang ang Clickjacking (bawal i-iframe ang portal sa ibang phishing site).
  • X-Content-Type-Options: nosniff – Pinipigilan ang MIME-type sniffing ng mga browser.
  • X-XSS-Protection: 1; mode=block – Built-in anti-XSS protection sa mga modernong browsers.

PART 4: Paano Pinoprotektahan ang Data ng Paaralan at Estudyante?

(Data Privacy Act of 2012 / RA 10173 Compliance)

1. Principle of Least Privilege & Strict Data Isolation

Ang bawat estudyante o guro ay may access lamang sa sarili nilang mga dokumento (WHERE user_id = :session_id). Hindi nila masisilip ang requests o attachment ng ibang tao.

2. Immutable Audit Trail & System Logs (Accountability)

Alinsunod sa RA 10173, ang bawat kritikal na galaw sa system ay awtomatikong itinatala sa audit_logs table:

  • User Name at Role: Sino ang gumawa?
  • Action Performed: Ano ang ginawa? (hal. Marked Request RQ-045 as Completed)
  • IP Address: Saan nanggaling ang request?
  • Exact Timestamp: Kailan nangyari?

Sagot Mo: "Mayroon po kaming automated Login Rate Limiting mechanism alinsunod sa OWASP standards. Pagkatapos ng limang (5) sunod-sunod na maling subok sa password, awtomatikong nagpapatupad ang system ng 15-minutong temporary cooldown. Hindi po kami nagpatupad ng permanent account lockout upang maiwasan ang Account Lockout Denial-of-Service (DoS) attack kung saan sadyaing ita-type ng attacker ang username ng guro o administrator upang sila ay ma-lock out. Sa aming approach, epektibong napapabagal ang automated bot guessing habang pinapayagan ang lehitimong user na makapasok muli matapos ang 15 minuto o agad sa pamamagitan ng One-Click Unlock ng Administrator."

Kapag ang computer sa library o computer lab ay naiwang nakabukas ng isang estudyante o guro, kusa pong pinapatay ng server ang session matapos ang 15 minutong walang galaw (inactivity) upang hindi ma-hijack ng ibang tao ang sensitibong rekord ng account."
